# Smart Parking Backend

FastAPI + SQLite backend for a smart parking system (ESP-01 sensors + admin dashboard).

## What changed from the original script

- No secrets hardcoded in source. `SECRET_KEY` and `ADMIN_PASSWORD_HASH` are now
  read from environment variables, and the app refuses to start if they're missing.
- Admin password is stored as a **bcrypt hash**, never plaintext.
- CORS origins are configurable via `CORS_ORIGINS` instead of allowing `*`.
- `DATABASE_URL` is configurable so the SQLite file can live on a persistent disk.
- Added a `GET /` health-check route (used by Render's health check).
- Added Docker + Render deployment files.

## Route groups (unchanged behavior)

- `/api/auth/login` — admin login, issues a JWT
- `/api/parking/update`, `/api/parking/config/{pack_id}` (GET) — called by the
  ESP-01 device, no auth
- `/api/parking/status`, `/api/parking/logs`, `/api/parking/config/{pack_id}` (POST)
  — called by the admin frontend, require a Bearer token

## Local development

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# fill in SECRET_KEY and ADMIN_PASSWORD_HASH in .env (see below), then:
export $(grep -v '^#' .env | xargs)   # or use a tool like python-dotenv / direnv

uvicorn backend_server:app --reload
```

### Generate the required secrets

```bash
# SECRET_KEY
python -c "import secrets; print(secrets.token_hex(32))"

# ADMIN_PASSWORD_HASH (prompts for a password, never prints it)
python generate_password_hash.py
```

## Running with Docker locally

```bash
docker build -t smart-parking-backend .
docker run --rm -p 8000:8000 \
  -e SECRET_KEY=<your-secret> \
  -e ADMIN_USERNAME=admin \
  -e ADMIN_PASSWORD_HASH='<bcrypt-hash>' \
  -e CORS_ORIGINS=http://localhost:3000 \
  -e DATABASE_URL=sqlite:///./parking.db \
  smart-parking-backend
```

Visit http://localhost:8000/docs for interactive API docs.

## Deploying to Render

### Option A: Blueprint (`render.yaml`) — recommended

1. Push this folder to a GitHub/GitLab repo.
2. In the Render dashboard, click **New > Blueprint** and point it at the repo.
   Render will read `render.yaml` and create the service automatically,
   including a 1GB persistent disk mounted at `/data` for the SQLite file.
3. `SECRET_KEY` is auto-generated by Render. You still need to set
   `ADMIN_PASSWORD_HASH` manually (it's marked `sync: false` so it isn't
   committed to git):
   - Run `python generate_password_hash.py` locally.
   - In the Render dashboard, open the service → **Environment** → add
     `ADMIN_PASSWORD_HASH` with the value it printed.
4. Update `CORS_ORIGINS` to your actual admin frontend URL once you know it.
5. Deploy. Your API will be live at `https://<your-service-name>.onrender.com`.

### Option B: Manual Web Service (Docker)

1. New > Web Service > connect your repo.
2. Runtime: **Docker** (it will pick up the `Dockerfile` automatically).
3. Add environment variables under the **Environment** tab:
   - `SECRET_KEY` (generate as above, or click "Generate" in Render)
   - `ADMIN_USERNAME` (e.g. `admin`)
   - `ADMIN_PASSWORD_HASH` (from `generate_password_hash.py`)
   - `ACCESS_TOKEN_EXPIRE_MINUTES` (e.g. `60`)
   - `CORS_ORIGINS` (your frontend's URL, comma-separated if more than one)
   - `DATABASE_URL` — if you want data to survive deploys, add a **Disk**
     (e.g. mount path `/data`) under the service's **Disks** tab, then set
     this to `sqlite:////data/parking.db`. Otherwise it defaults to a local
     file that resets on every deploy.
4. Health check path: `/`
5. Deploy.

### Pointing your ESP-01 / frontend at it

- ESP-01 firmware: point its HTTP requests at
  `https://<your-service-name>.onrender.com/api/parking/update` and
  `.../api/parking/config/{pack_id}`.
- Admin frontend: point login/API calls at
  `https://<your-service-name>.onrender.com/api/...` and make sure that
  frontend's origin is included in `CORS_ORIGINS`.

**Note on Render's free tier:** free web services spin down after periods of
inactivity and take a few seconds to wake up on the next request — expect a
cold-start delay if the ESP-01 posts infrequently.
